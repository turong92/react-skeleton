# @skeleton/auth

인증 조각 — 백엔드 `modules/auth` · `modules/auth-social`(+ 제공자 모듈 google · kakao · naver · oidc(LINE) · x) 계약을 그대로 부르고, 토큰을 들고, 라우트를 지킨다.
의존: `@skeleton/api-client` · `@skeleton/ui`(화면). peer: `react` `react-router-dom`.

```tsx
// 기본 저장소는 localStorage + crossTab(탭 사이 로그인 · 로그아웃 · 갱신 공유). 탭마다 따로면 sessionStorage, storage 생략 = 메모리만
const keys = authStorageKeys('my-app') // 저장 키 · 락 · 채널 이름을 앱 이름으로 나눈다(같은 출처의 앱끼리 토큰이 섞이지 않게)
const tokenStore = createTokenStore({ storage: window.localStorage, storageKey: keys.accessToken, crossTab: true })
const refreshStore = createRefreshStore({ storage: window.localStorage, storageKey: keys.refresh, crossTab: true })
const apiClient = createApiClient({
  ...,
  getAuthHeaders: createAuthHeadersProvider(tokenStore),
  onError: createUnauthorizedHandler({ store: tokenStore, refreshStore }), // 복구할 수 없는 401 → 두 저장소 삭제(+ onUnauthorized)
})
const authSession = createAuthSession({ api: createAuthApi(apiClient), store: tokenStore, refreshStore, refresher })
// 로그아웃 · 다른 탭의 로그아웃 · 갱신 실패 · 다른 계정의 링크 로그인 — 계정이 사라지거나 바뀔 때마다 서버 상태 캐시를 비운다
onAccountChange(authSession, () => queryClient.clear())

<AuthProvider session={authSession}> … </AuthProvider>
{ element: <RequireAuth redirectTo="/login" />, children: [{ path: '/account', element: <Account /> }] }
const { status, principal, login, logout } = useAuth()
```

소셜 로그인 — 로그인 버튼과 콜백 페이지(`/auth/callback`)가 같은 `flow` 를 쓴다. 제공자 화면에 다녀오면 페이지가 새로 뜨므로 `state` 는 `sessionStorage` 에 둔다:

```tsx
const social = createSocialLoginFlow({
  session: authSession, // socialLogin(provider, code, redirectUri) 를 가진 것
  storage: window.sessionStorage,
  providers: discovered.providers, // GET /auth/methods → methodsFromInfo(info).providers — authorize 주소 · scope · pkce · nonce 가 들어 있다
})
const { url } = await social.start('line') // 비동기(WebCrypto SHA-256) — PKCE 필수인데 WebCrypto 가 없으면 PkceUnavailableError
window.location.assign(url) // 로그인 버튼
// 콜백 페이지: const result = useSocialLoginCallback(social, location.search) → 'pending' | 'success' | 'error'
```

제공자 목록 · 순서 · authorize 주소 · scope · `pkce`/`nonce` 요구는 모두 백엔드의 `GET /auth/methods` 가 말해 준다(`createAuthRoutes({ discovery })` 가 알아서 쓴다) — 프런트에는 제공자 주소가 없다(authorize 정보를 안 보내는 옛 백엔드용 `SOCIAL_AUTHORIZE_PRESETS` 는 **LEGACY** 대체 표). 버튼의 마크 · 문구는 제공자 코드로 붙는다(`providerPresentation` — google · line · x · kakao · naver, 모르는 코드는 중립 마크; 문구는 `labels.providerSignInText` / `signInWithProvider`). `clientId` 는 공개값(authorize 주소에 실린다). `clientSecret` 은 백엔드 `skeleton.auth-social.providers.*` 에만 있다. 이 흐름은 백엔드 계약(`OAuthSocialLoginRequest`)까지만 안다 — scope 의 의미 · 계정 연결 정책(`LinkedAccountOnly…`)은 백엔드 설정이다.

## 실제 제공자 붙일 때 (Google · LINE · X)

**1. 콜백 주소를 제공자 콘솔에 글자 그대로 등록한다.** 이 앱이 내놓는 주소는 둘이다 — 로그인용과 (설정에서 하는) 연결 · 다시 인증용. 제공자는 `redirect_uri` 를 **정확히** 비교한다(http/https · 호스트 · 포트 · 끝 슬래시 하나만 달라도 `redirect_uri_mismatch`).

| 쓰임                                                                              | 로컬(Vite 기본 포트)                                                                               | 배포                                     |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 로그인 · 가입 (`/auth/callback`)                                                  | `http://localhost:5173/auth/callback` · X 는 `http://127.0.0.1:5173/auth/callback`                 | `https://<도메인>/auth/callback`         |
| 계정 연결 · 이메일 변경 · 연결 해제 · 삭제의 다시 인증 (`/account/link-callback`) | `http://localhost:5173/account/link-callback` · X 는 `http://127.0.0.1:5173/account/link-callback` | `https://<도메인>/account/link-callback` |

- **X 는 `localhost` 를 거부한다** — 개발 서버를 `127.0.0.1` 로 열고(`vite --host 127.0.0.1`) 그 주소로 등록 · 접속한다. LINE 이 http `localhost` 를 허용하는지는 콘솔에서 확인(안 되면 https 터널 주소).
- 두 주소를 **모두** 등록한다(Google 은 여러 개 가능 · LINE 은 Callback URL 칸에 여러 줄 · X 는 Callback URI 여러 개). 로그인 요청의 `redirectUri` 는 그 인가 요청에 쓴 값과 같아야 하므로 이 패키지가 시작 때 저장한 값을 그대로 보낸다.
- 백엔드가 `redirectUri` 를 알려 주면(`skeleton.auth-social*.providers.*.redirect-uri`) 그 값이 이긴다 — 이 앱의 콜백과 **출처 · 경로 · 끝 슬래시**가 다르면 개발 콘솔에 어디가 다른지 경고한다(`redirectUriProblems`). 백엔드 값은 보통 비워 두고 앱이 자기 출처로 만든다.
- 시작한 탭에서 끝내야 한다(`state` · verifier · nonce 는 그 탭의 `sessionStorage`). 모바일에서 LINE 앱 · 인앱 브라우저가 콜백을 **다른 브라우저/탭**으로 열면 「이 탭에서 시작한 로그인이 아니에요」 안내가 뜬다 — 같은 브라우저에서 다시 시작한다.
- **인가 코드 수명**: LINE 10분 · **X 30초** · 그 밖은 비공개 — 콜백을 받으면 바로 백엔드로 보낸다(이 패키지는 `complete` 안에서 곧바로). 같은 코드를 두 번 쓰지 않는다(StrictMode 이중 실행도 로그인은 한 번).
- 제공자가 이메일을 안 주거나 믿을 수 없다고 하면(LINE · X) 주소 없는 계정이 된다 — 설정은 「주소 없음」으로 그리고 「이메일 추가」는 LINE/X 동의를 다시 거친다(새 `state` · verifier · nonce).

백엔드 쪽 콘솔 설정(Channel ID · secret · 이메일 권한 · 테스터 등록)은 kotlin-skeleton 의 `docs/modules/auth-social-oidc.md` · `auth-social-x.md` 체크리스트를 따른다.

## PKCE · nonce — 시도마다

시작할 때마다 `state`(24바이트) · `codeVerifier`(32바이트 → 43자 base64url) · `nonce`(제공자가 쓸 때)를 CSPRNG 로 만들어 탭 `sessionStorage` 의 `state` 키 아래에 **제공자 · 종류(login · link · reauth) · 계정**과 함께 둔다 — 한 번 읽으면 지워진다. `code_challenge = BASE64URL(SHA-256(verifier))`(S256 뿐) 만 URL 에 간다. 로그인 · 연결(최상위) · `socialReauth`(이메일 변경 · 연결 해제 · 삭제)에 `codeVerifier` · `nonce` 를 싣는다. 콜백 주소로 돌아온 `state`(비교를 마친 값)도 **모든 제공자에** 같은 자리에 `state` 로 싣는다 — 서버가 토큰 요청에 필요한 제공자(Naver)에만 쓰고 나머지는 무시한다. `state` 는 로그 · 오류 · 저장소에 따로 남기지 않는다. `pkce: UNSUPPORTED` 제공자에는 PKCE 파라미터를 보내지 않는다(모르는 파라미터를 거절하는 곳이 있다). 400 `AUTH.SOCIAL_PKCE_FAILED` · `AUTH.SOCIAL_NONCE_FAILED` 는 요청이 잘못 만들어진 것(아직 아무것도 쓰이지 않았다), 401 `AUTH_SOCIAL.INVALID_AUTHORIZATION_CODE` · `AUTH.SOCIAL_ID_TOKEN_INVALID` 는 동의를 처음부터 다시.

## 계정 수명주기 — 라우트 한 벌

```tsx
import { createAuthRoutes, koAuthLabels } from '@skeleton/auth'

export const accountRoutes = createAuthRoutes({
  session: authSession, authApi, accountApi,          // createAuthApi · createAccountApi(apiClient)
  // 로그인 방법: 둘 중 하나. 백엔드(GET /auth/methods)에 묻거나(discovery) 앱이 직접 정한다(methods — 이것이 이긴다)
  discovery: { delivery: 'body', social: { session: authSession, storage: window.sessionStorage } },
  // methods: { password: true, magicLink: true, social: [{ provider: 'google' }] },
  // socialFlow, socialLinkFlow,                       // methods 로 직접 정할 때만(createSocialLoginFlow · createSocialLinkFlow) — discovery 는 백엔드가 준 제공자로 만든다
  labels: koAuthLabels,                                // 기본 영어. 언어가 바뀌는 앱은 useLabels: () => 문구(훅)
  signUp: { consents: [...], renderCaptcha: ... },     // false 면 가입 라우트가 없다. 객체면 캡차 · 동의 슬롯
  forgotPassword: true, settings: { locales, sections: { delete: false } },
})
// routes: [{ element: <Layout />, children: [...accountRoutes, ...] }]
```

생기는 경로(`paths` 로 바꾼다): `/login` `/sign-up` `/forgot-password` `/reset-password` `/forgot-id`(아이디를 켠 서버일 때 — `discovery` 라우트에서만) `/magic-link`(방법이 켜졌을 때 — `discovery` 면 늘) `/auth/callback`(`socialFlow` 가 있거나 `discovery` 일 때) · 로그인한 사람만 `/account` `/account/link-callback`. **링크가 남은 곳은 비밀번호 재설정과 링크 로그인뿐**(그 흐름에는 세션이 없다). 가입 인증 · 이메일 변경 · 다시 인증 · 삭제 확인은 6자리 인증번호를 그 자리에서 입력한다. 오래된 메일의 링크(`/verify-email` `/confirm-email-change` `/confirm-reauth` `/confirm-delete` — `legacyLinks` 로 바꾸거나 `false`)는 토큰을 읽지 않고 「이 링크는 더 이상 쓰이지 않아요」 한 장으로 보낸다. 서버 렌더 앱은 `useApis`(요청마다 API) · `guard`(하이드레이션 안전판)를 쓴다 — SSR 스타터의 `src/auth/routes.tsx`.

**로그인 방법 — 백엔드가 알려 준다** — 기본은 `discovery`: 라우트가 `GET /auth/methods`(공개 · 캐시 가능 — 방법 · 가입 열림 · 소셜 제공자와 공개 clientId · 리프레시 전달 방식)를 물어 그대로 따른다. 모르는 동안(로딩)에는 로딩 화면 — 환경변수 기본값 같은 **틀린 방법이 깜박이지 않는다**(서버 렌더도 로딩 화면을 그리고 브라우저가 묻는다). 못 물으면(네트워크 · 옛 백엔드) `fallback`(기본 비밀번호만)과 「다시 시도」 줄. 답은 한 API 당 5분 공유(`loadAuthMethods`). 앱이 `methods` 를 직접 주면 그것이 이기고 묻지 않는다(환경변수 `VITE_AUTH_METHODS` 덮어쓰기 · `new-project.sh --auth-methods a,b` 로 고정). 소셜 버튼은 clientId 가 있는 제공자만(백엔드가 모르면 앱이 `VITE_SOCIAL_<제공자>_CLIENT_ID` 를 준다). 리프레시 전달 방식(`body` · `cookie`)은 시작할 때 정해야 하므로 앱 설정이고, 백엔드와 다르면 개발 콘솔에 경고한다(`deliveryMismatch`).

**가입 = 인증번호** — `POST /account/sign-up` 은 계정을 만들지 않고 `202 {status, signUpId}` 만 준다(주소가 새것이든 이미 있든 같은 모양). 메일의 6자리를 같은 화면에서 입력하면(`VerifyCodePanel` · `CodeEntry`, 6자리를 채우면 버튼 없이 제출) `POST /auth/verify-email {signUpId, code}` 가 계정을 만들고 **바로 로그인**시킨다(응답이 토큰, `X-Device-Name` 도 실린다). 틀리면 `ACCOUNT.CODE_INVALID` + 남은 횟수(`data.attemptsLeft`)를 보이고 칸을 비운다. 만료 · 소진 · 이미 씀은 `ACCOUNT.CODE_EXPIRED`(410, 한 가지 응답) → 처음부터. 「새 코드」는 `POST /account/verification/resend {signUpId}`(30초 쿨다운). 진행 중인 시도(`signUpId` + 주소 — 비밀번호는 아니다)는 그 탭의 `sessionStorage` 에 둬 코드 단계에서 새로고침해도 이어진다. 메일 인증을 끈 백엔드는 `201 CREATED`(signUpId 없음)라 바로 로그인 화면으로 간다.

**인증번호 남은 시간** — 모든 코드 단계(가입 · 이메일 변경 · 다시 인증 · 삭제 확인)가 `CodeEntry` 의 `mm:ss` 를 보인다. 만료 시각은 절대 시각이고 시계는 `createAuthRoutes({ now })`(서버 `Date` 헤더로 보정한 `serverClock`). 출처: 가입 · 이메일 변경 요청 · 재인증 · 삭제 확인 모두 **요청 응답의 `expiresAt` · `resendAvailableAt`(ISO-8601)이 있으면 그 값**(`codeWindowOf` — `createAccountApi` 가 세 요청의 응답을 돌려준다, `CodeSent`), 없으면(옛 서버) 문서화된 유효 시간으로 **어림**(`codeTtlSeconds` 기본 600 = 백엔드 기본 10분, `data-expiry-source="estimate"`). 이메일 변경은 새로고침 뒤 `me.pendingEmailExpiresAt`. 만료된 가입 시도의 「다시 받기」는 새 백엔드가 새 번호를 보내므로 먼저 같은 시도에 다시 받기를 해 보고, 응답에 새 `expiresAt` 이 있으면 그 자리에서 타이머를 다시 시작(보관 상태도 갱신), 없으면(옛 서버) 처음부터 다시(양식)로 이어진다. 가입 보관 상태에는 시각만(코드 · 비밀번호 없음).

**탈퇴 유예 중인 계정의 로그인 — 「탈퇴를 취소할까요?」** — 비밀번호 · 링크 · 소셜 어느 수단이든 맞는 증거로 들어오면 서버가 세션 대신 `403 AUTH.ACCOUNT_DELETION_PENDING`(`data.purgeAfter`, 서버가 `skeleton.account.deletion.self-restore` 를 켰을 때만 `data.restoreToken` · `restoreTokenExpiresAt`)을 준다. 세 길(`SignInScreen` · `MagicLinkLanding` · `SocialCallbackScreen`)이 같은 `DeletionPendingScreen` 을 그린다: 「이 계정은 탈퇴 처리 중이에요. {날짜}에 완전히 지워져요」 + [탈퇴 취소하고 계속 쓰기] + [그대로 두기]. 취소 = `authApi.cancelDeletion(restoreToken)`(`POST /account/delete/cancel`, 공개) → 일반 로그인 응답이라 `auth.cancelDeletion` 이 `login` 과 똑같이 세션을 저장하고 라우트 페이지가 가려던 곳으로 보낸다(약관 재동의 등 로그인 뒤 처리 그대로). `410 ACCOUNT.TOKEN_INVALID` 는 「시간이 지났어요. 다시 로그인해 주세요」, 그 밖의 실패는 문구 + 같은 토큰으로 다시. **`restoreToken` 은 화면의 메모리에만 있다**(저장소 · 주소 · 마크업에 없음 — 새로고침하면 다시 로그인). 토큰이 없으면(서버가 껐다) 버튼 없이 안내만(「되돌리려면 문의해 주세요」). 날짜는 `settings.formatDate`(없으면 브라우저 로케일). 직접 짠 화면은 `deletionPendingOf(error)` 로 같은 값을 읽는다. 삭제 완료 안내는 앱이 서버의 self-restore 를 안다고 알릴 때만(`settings: { selfRestore: true }`) 「기간 안에 다시 로그인하면 취소할 수 있어요」를 더한다 — 꺼진 서버에서 거짓이 되지 않게 기본은 말하지 않는다. 정지된 계정의 탈퇴(`ACCOUNT.SUSPENDED_CANNOT_DELETE`) · 막힌 주소의 가입 인증 · 링크 · 소셜(`ACCOUNT.REGISTRATION_BLOCKED`)은 각자의 문구로 말한다(`errors.ts`).

**같은 이메일의 계정이 이미 있을 때(소셜 로그인 `409 ACCOUNT.SOCIAL_EMAIL_CONFLICT`)** — 자동으로 합치지 않는다(본문 `data` 도 없다: 어떤 방법으로 가입했는지는 존재 노출이라 주지 않는다). `/auth/callback` 은 막다른 오류가 아니라 **안내 화면**을 그린다 — 「이미 이 이메일로 가입한 계정이 있어요」 + 가입할 때 쓴 방법으로 로그인한 뒤 설정의 「로그인 수단」에서 그 소셜을 직접 연결하라는 문장(제공자 이름 뒤에 조사를 붙이지 않는 구조) + 주 단추 「로그인하러 가기」 · 보조 「처음으로」. 로그인에 성공하면 `/account#methods` 로 가고(`linkIntentState` — 로그인 화면이 이미 읽는 `state.from` 관례라 `safeReturnPath` 검사를 그대로 거친다), 그 구역이 「{제공자} 연결을 이어서 하세요」 한 줄과 강조 테두리 + 포커스가 간 「연결」 단추를 보인다(`AccountSettings` 의 `linkIntent`; 이미 연결됐거나 앱이 안 켠 제공자면 아무것도 더하지 않는다). 의도(어느 제공자)는 **router state 로만** 옮긴다 — 저장소 · 주소 쿼리에 넣지 않는다(새로고침하면 사라져도 된다). 어느 제공자였는지는 `flow.providerOfFailure(error)`(`flow.complete` 가 거절된 오류를 그 제공자와 따로 기억한다 — 오류 객체는 그대로). 콜백은 이메일을 주지 않으므로 로그인 화면의 이메일 칸은 **미리 채우지 않는다**. 이메일이 없는 계정(주소를 안 주는 Google 등)은 설정에서 「이메일 주소가 없어요」 + 새 주소 추가(제공자 동의를 다시 거침)로 보인다.

**이메일 필수 — 주소 없는 계정을 막고, 등록하게 한다**(기본 꺼짐 · 백엔드 `skeleton.account.email.required=true` 인 앱) — 카카오 · 네이버 · X · LINE · 비-Gmail 구글로 가입한 계정은 주소가 없다. 서버는 허용 목록(`GET /account/me` · `POST /account/email/change`(+`/confirm`) · `POST /account/delete`(+`/confirmation`) · `/auth/**` · `/legal/**`) 밖의 모든 호출에 `403 ACCOUNT.EMAIL_REQUIRED` 를 주고 `me.emailRequired` 는 `true`(켠 앱에서만 키가 있다). 화면은 이렇게 잇는다 — 앱 코드는 네 군데뿐이다(sample 의 `api/emailRequired.ts` · `api/client.ts` · `auth/EmailGate.tsx` · `main.tsx` 가 정본):

1. `const emailRequired = createEmailRequiredController()` — API 클라이언트보다 먼저.
2. `createApiClient({ recoverForbidden: chainForbiddenRecovery(emailRequired.recover, reconsent.recover) })` — 403 을 붙잡았다가 등록이 끝나면 **그대로 한 번 더** 보낸다. 순서는 서버 인터셉터와 같다(이메일 → 약관). 이 403 은 쿼리도 뮤테이션도 오류 토스트로 새지 않는다(`isEmailRequiredError` 를 전역 토스트에서 뺀다).
3. `<EmailRequiredGate controller api={accountApi} accountId onSignOut onDelete …>` 를 `AuthProvider` 안, 약관 막 **바깥**에 한 번. 주소가 없으면(로그인 직후 `me` 또는 403) 아래를 `inert` 로 두고 「이메일을 등록해 주세요」 전면 화면(`EmailRequiredScreen`)이 덮는다 — 한 번에 하나, 이메일 → 약관 → 닉네임. 계정 설정(`/account`)에서 등록하거나 삭제하는 동안은 `standAside` 로 막을 걷는다. 게이트가 지금 계정(`accountId`)을 컨트롤러에 알려(`setAccount`) 계정이 바뀌면(다른 탭이 다른 계정으로 로그인 · 로그아웃) 막이 접히고 붙잡은 호출은 원래 403 으로 끝난다 — 다른 계정의 토큰으로 나가지 않는다. 막이 열려 있는 동안 탭이 다시 보이면 서버에 다시 묻는다(`enabledProviders` 는 앱이 켠 소셜 제공자만 재동의 단추로). 약관 막(`ReconsentGate`)은 `emailRequired.isReady()` 가 true 이고 `getState().status` 가 `idle` 일 때만 `accountId` 를 받게 한다(sample `legal/LegalGate.tsx`) — 안 그러면 서버에 묻기 전 · 설정에서 등록하는 동안 약관 막이 먼저 뜬다.
4. `createAuthRoutes({ emailRequired })` — 설정에서 첫 이메일이 확인되면 막을 걷는다.

화면: 주소 → 6자리 인증번호(서버의 `expiresAt` · `resendAvailableAt` 로 센다) → 끝나면 막혔던 호출이 이어진다. **현재 세션은 유지되고 다른 세션만 닫힌다**(서버 `revokeAll(account, currentSession)`). 이미 다른 계정이 쓰는 주소는 서버가 같은 202 를 주고 번호는 가지 않으므로 번호 화면에 「번호가 안 오면 그 주소로 이미 가입한 계정이 있을 수 있어요 — 그 계정으로 로그인해 설정에서 {제공자} 연결을 눌러 주세요」 안내가 늘 있다. 마지막 로그인이 1시간을 넘었으면 `403 ACCOUNT.REAUTH_REQUIRED` — 「보안을 위해 {제공자}로 한 번 더 확인해 주세요」 + 채운 단추, 누르면 계정 설정이 열리자마자 그 제공자 동의 화면으로 가고(`emailReauthState`) 돌아오면 설정의 이메일 구역이 인증번호를 이어 보낸다. 막다른 길이 없다: 로그아웃 · 「내 계정 삭제」(허용 목록에 있다 — 이메일 등록 전 설정은 이메일 등록과 삭제 구역만 그린다). `EmailSection` 은 주소 없는 계정의 **첫 등록에 다시 인증을 내밀지 않는다**(서버가 요구할 때만).

**로그인 아이디 — 서버가 켰는지는 응답이 말한다**(기본 꺼짐 · 백엔드 `skeleton.account.login-id.enabled=true` 인 앱 · 계약 FINAL-7 L1~L13) — 앱이 따로 맞추는 값은 없다.

- **켜짐을 아는 법**: `GET /auth/methods` 의 **`loginId: { minLength, maxLength }` 키**(발견 — `useAuthMethods` · `methodsFromInfo` 가 `loginId` 규칙을 준다, 규칙이 쓸 만하지 않으면 키가 없는 것으로 읽는다) · `GET /account/me` 의 **`me.loginId`**(문자열 = 정했다 · `null` = 정해야 한다, 허용 목록 밖의 호출은 `403 ACCOUNT.LOGIN_ID_REQUIRED` · **키가 없으면 꺼진 서버**) · `me.emailRequired` / `me.emailRequiredToWrite`(아래 「이메일을 받는 시점」). **키가 없으면 모든 화면이 예전과 같다**(옛 서버 · 아이디를 안 쓰는 서버).
- **켜면 생기는 것**: 가입의 아이디 칸(`LoginIdField` + `useLoginIdAvailability` — 입력이 멈춘 0.4초 뒤 형식이 맞을 때만 `POST /account/login-id/availability`, 늦게 온 답은 버리고 같은 값은 다시 묻지 않는다, 상태는 색이 아니라 글자 + `aria-live`) · 인증번호 단계에서 아이디가 그 사이 나갔을 때 그 자리에서 다시 받는 `LoginIdRetry`(같은 `signUpId` · 같은 코드) · 로그인 칸 「아이디 또는 이메일」(`@` 가 있으면 `email`, 없으면 `username` — 입력을 본문으로 바꾸는 곳은 `signInCredentials` 한 군데) + 「아이디 찾기」 링크 · `/forgot-id` 의 `ForgotLoginIdScreen`(비밀번호 찾기와 같은 틀 · 같은 캡차 자리, 늘 「있다면 보냈다」) · 아이디 없는 계정이 앱 대신 보는 `LoginIdGate` · 설정의 아이디 줄 · 관리자 표의 「아이디」 열과 찾기.
- **지원하지 않는 조합 — `methods` 를 환경변수 등으로 덮어써 발견을 끈 앱**(`VITE_AUTH_METHODS` · `new-project.sh --auth-methods`): 아이디 화면 셋(**가입 칸 · 로그인 칸 라벨 · `/forgot-id`**)이 켜지지 않는다 — 켜짐을 알려 주는 것이 발견뿐이기 때문이다. 그 앱을 아이디를 켠 서버에 붙이면 가입 본문에 `loginId` 가 없어 서버가 400 으로 거절한다. 아이디를 켠 서버에 붙이는 앱은 발견을 쓴다. (막 `LoginIdGate` · 설정의 아이디 줄은 `me.loginId` 를 읽으므로 켜지지만 길이 규칙은 서버 기본 4~20 으로 짐작한다.)
- **아이디 정하기**: `POST /account/login-id`(이메일도 다시 인증도 필요 없다) — **정한 뒤에는 바꿀 수 없다**(바꾸는 API 가 없다 · `409 LOGIN_ID_ALREADY_SET` 은 다른 탭에서 이미 정한 것이라 화면이 다시 읽고 막을 접는다). 내기 전에 **확인 대화상자**(「○○(으)로 정할까요? 정한 뒤에는 바꿀 수 없어요」)가 한 번 있다. 설정의 아이디 줄은 세 모습 — 정한 아이디(값 + 「바꿀 수 없어요」, 고치는 입력 없음) · 아직 안 정함(같은 칸 · 같은 확인으로 여기서 정한다 — 이때 `/account` 는 아이디 정하기 · 이메일 · 계정 삭제만 연다) · 소셜로만 들어온 계정의 안내(「비밀번호를 만들면 아이디나 이메일로도 로그인할 수 있어요」 + 비밀번호 구역 단추, 주소가 없으면 이메일 구역 단추). 아이디는 어떤 공개 응답 · 화면 · 주소에도 나오지 않는다(백엔드 L13) — 토큰 · `GET /auth/me` 에도 없다.
- **관리자 표**(`@skeleton/auth/admin`): 응답에 `loginId` 키가 있으면 「아이디」 열(아직 안 정했으면 `-`)과 「아이디로 찾기」 칸이 생긴다. 찾기는 **정확히 일치만**이고 질의는 Enter 나 「찾기」 단추를 눌렀을 때만 나간다(입력 중에는 서버에 가지 않는다 — 조각이 주소 · 로그에 남지 않게). 결과가 비어도 칸은 남는다(`showLoginId` · 목록을 부르는 `AdminAccounts` 는 한 번 켜지면 계속 켠다). 키가 없는 서버에서는 열도 칸도 없다.

**이메일을 받는 시점 — 안 받음 · 쓰기 때 · 로그인 직후**(백엔드 `email.required` + `required-when`, 계약 E7~E12) — 앱의 선택이고 서버가 `me` 로 말한다: `me.emailRequired === true` 면 **로그인 직후** 막이 덮는다(지금까지의 동작). `me.emailRequiredToWrite === true`(키는 이 방식에서만 있다)면 **쓰기 때** — 주소 없는 계정도 읽기는 되고 변경 요청만 `403 ACCOUNT.EMAIL_REQUIRED` 다. 둘 다 없으면 받지 않는다. 쓰기 때 방식에서는:

- 쓰기의 403 이 이메일 등록 화면을 열고(쓰기용 제목 · 테두리 단추 「나중에 하기」), 등록이 끝나면 붙잡은 호출이 **같은 `Idempotency-Key` · 본문으로 한 번 다시 나간다**(`Idempotency-Key` 는 호출이 `idempotencyKey` 를 넘겼을 때만 있고, 같은 요청 객체를 다시 보내므로 같은 키가 간다). 「나중에 하기」로 닫으면 붙잡은 호출은 원래 403 으로 끝나고 `<EmailRequiredGate onLater>` 가 불린다 — 전역 토스트는 이 코드를 걸러 아무 말이 없으므로 앱이 `labels.emailRequiredDeclined` 한 줄을 낸다(sample `EmailGate`).
- **쓰기 전 확인**: `const { needed, ensure } = useEmailBeforeWrite(emailRequired)` — 글쓰기 화면으로 가기 **전에** `if (!ensure()) return`(boolean — 이메일이 필요하면 등록 화면을 열고 `false`, 등록이 끝난 뒤 **사용자가 다시 누른다**. 글을 다 쓴 뒤에야 막히면 제공자 재확인 왕복에서 글을 잃는다). 로그인 직후 방식 · 받지 않는 앱 · 주소가 있는 계정은 늘 `true`. 댓글 칸처럼 늘 보이는 입력 위에는 막지 않는 띠 `<EmailWriteNotice controller labels />`(주소 없는 계정에게만 그려진다).
- **제공자 재확인으로 떠나면 쓰던 글은 사라진다** — 마지막 로그인이 오래돼 `REAUTH_REQUIRED` 면 제공자 동의 화면으로 페이지가 떠나고(주소 없는 계정에는 이쪽이 흔한 길), 화면이 떠나기 전에 「쓰던 내용은 사라져요」(`emailRequiredReauthLosesDraft`)를 말한다. 글을 보존하는 초안 저장은 없다.
- 열려 있는 동안 「다른 탭에서 이미 등록했나」의 판정은 `emailRequired` 가 아니라 **주소가 있는가**(`stillNeedsAddress` — 쓰기 때 서버에서 `emailRequired` 는 늘 `false` 라 그 값만 보면 막이 뜨자마자 접힌다). 그래서 **쓰기 때 서버에 이전 프론트를 붙이면 이메일 막이 뜨자마자 접힌다 — 백엔드와 프론트는 한 묶음으로 내보낸다.**
- 이메일이 없는 설정: 비밀번호 · 연락받을 이메일 · 로그인 수단 구역은 서버가 403 으로 막으므로 「이메일을 등록한 뒤에 할 수 있어요.」(`settingsNeedsEmail`) + 테두리 단추로 접고, 이메일 구역은 왜 필요한지 한 줄(`settingsEmailToWrite`)을 말한다. 프로필 · 이메일 · 세션 · 삭제는 그대로 열려 있다.
- `POST /account/discard`(「이미 계정이 있나요?」)의 뜻은 「등록 미완료 계정」이 아니라 **「이메일이 없는, 아무것도 쓰지 않은 계정」**이다. 이미 아이디를 정한 계정도 버릴 수 있고, 그 아이디는 다시 쓰이지 않는다(확인 문구가 `emailRequiredDiscardConfirmLoginId` 로 아이디를 말한다).
- **`/account` 에서는 「나중에 하기」가 없다**: 쓰기 때 방식 + 막이 걷힌 계정 설정(`standAside`)에서는 그려질 화면이 없어 쓰기의 403 을 붙잡지 않고 `decline()` 으로 원래 403 으로 끝낸다 — `onLater` 는 불리지 않는다(사용자가 누른 것이 아니다). 전역 토스트가 이 코드를 걸러 아무 말이 없으므로, **앱이 `/account` 에 붙인 자기 쓰기 구역**은 주소 없는 계정에게 말없이 실패한다 — 그 구역이 `isEmailRequiredError` 로 이유를 직접 말하거나 이메일 구역으로 안내한다. (패키지의 설정 구역은 서버가 막는 것을 이미 「이메일을 등록한 뒤에 할 수 있어요.」로 접는다.)
- **네이티브 모달(`<dialog>`) 안에서 막힌 쓰기를 보내지 말 것 — 열기 전에 `ensure()`**: 이메일 화면은 top layer 밖의 고정 요소라, 모달이 열려 있으면 브라우저가 그 밖의 문서를 `inert` 로 만들어 화면이 backdrop **밑**에 깔리고 눌리지 않는다(모달 쪽은 저장이 붙잡혀 「저장 중」으로 남는다). 화면을 top layer 로 올려도(`popover`) 소용없다 — 모달 뒤에 연 popover 도 `inert` 다(브라우저 실측). 되는 길은 이메일 화면을 두 번째 `<dialog>.showModal()` 로 만드는 것뿐인데, 막 셋(아이디 · 이메일 · 약관)의 포커스 · `inert` · Esc 규칙을 모두 다시 써야 해서 하지 않았다. 규칙: **모달 안에서 쓰기를 보내는 모든 입구는 모달을 열기 전에 `useEmailBeforeWrite` 의 `ensure()` 를 거친다** — sample 의 닉네임 대화상자(띠 · 선택기 · 쓰기 전 확인 모두 `useNicknameDialog` 한 곳) · 노트 · 글 삭제 확인 창 · 게시판 `BoardComments` 의 `beforeDelete` · `AuthorProfileManager` 의 `beforeRemove` 가 그렇게 한다. 이메일 화면이 열렸으면 모달은 열지 않고, 사용자가 등록한 뒤 다시 누른다.
  - **알려진 예외 - 관리자 정지 확인 창**(`AdminAccountsTable` 의 `ConfirmDialog`)은 창 안에서 변경 요청을 보내는데 열기 전 확인이 없다. 주소 없는 계정이 ADMIN 인 좁은 경우에만 이메일 화면이 창 밑에 깔린다(코드는 그대로 둔다).
  - **잔여 위험**: `ensure()` 는 서버가 언제 주소를 요구하는지 아직 모르는 동안(`when === 'unknown'` - 이메일 막의 `me` 가 아직 오지 않았거나 실패한 동안)에는 통과시킨다. 그 틈에는 모달이 열릴 수 있다.
  - **계정 설정(`/account`)에서는 막이 걷혀 있다**(`standAside`): `ensure()` 가 `false` 를 줘도 화면이 뜨지 않고 곧바로 접힌다. 거기서 `ensure()` 를 앞에 둔 단추는 말없이 죽지 않도록 한 줄(`labels.emailRequiredDeclined`)을 띄우고 같은 화면의 이메일 구역(`#email`)으로 보낸다 - sample 의 `useNicknameDialog`.
- **업그레이드할 때 눈에 띄는 변화**(키가 없는 서버에서도): `SignInScreen` 의 `onPasswordSignIn` 인자는 합집합 `SignInCredentials`(`{ email, password }` | `{ username, password }`)다 — 인자 타입을 `{ email: string; password: string }` 으로 직접 적은 앱은 타입 오류가 나므로 `SignInCredentials` 로 받는다. 관리자 표의 빈 상태 제목은 h3 → h2 다(쪽 제목 `h1` 바로 아래). 키가 없는 서버에서 바뀌는 마크업은 이것 하나뿐이다.

**막 셋을 붙이는 법 — 아이디 → 이메일 → 약관**(서버 인터셉터와 같은 순서 · 켜지 않는 막은 빼도 된다 · sample `main.tsx` · `api/client.ts` · `auth/LoginIdGate.tsx` · `auth/EmailGate.tsx` · `legal/LegalGate.tsx` 가 정본):

1. **컨트롤러를 API 클라이언트보다 먼저** 만든다: `createLoginIdRequiredController()` · `createEmailRequiredController()` · `createReconsentController(…)`(약관은 `@skeleton/legal`).
2. `createApiClient({ recoverForbidden: chainForbiddenRecovery(loginIdRequired.recover, emailRequired.recover, reconsent.recover) })` — 순서가 곧 서버의 게이트 순서다.
3. **전역 오류 토스트에서 `isLoginIdRequiredError` · `isEmailRequiredError` 를 뺀다**(쿼리 · 뮤테이션 모두 — 막이 말하는 403 이 토스트로도 새지 않게).
4. `<LoginIdGate controller api={accountApi} accountId rules onSignOut onDiscarded …>` → `<EmailRequiredGate …>` → 약관 막(`ReconsentGate`) → 라우터 순으로 `AuthProvider` 안에 **바깥에서 안으로** 감싼다. `rules` 는 발견의 `loginId`(sample `useLoginIdRules`).
5. **막은 라우터 밖이다.** 라우터 컨텍스트가 없으므로 「계정 설정」 링크는 `onOpenSettings` 에 바깥 핸들(`() => router.navigate('/account')`)을 꽂거나, 안 꽂으면 기본 `<a href>` 로 **전체 이동**한다.
6. **`/account` 에서는 `standAside`** — 설정에서 아이디를 정하고 이메일을 등록하고 계정을 지울 수 있어야 하므로 계정 설정 쪽 경로면 막을 걷는다(컨트롤러 상태는 그대로). 쓰기 때 방식에서는 이메일 막도 같다(`/account` 에서 막이 걷혀 이메일 구역이 보인다).
7. **안쪽 막은 바깥 막이 `isReady()` 이고 `getState().status === 'idle'` 일 때만 서버에 묻는다** — 이메일 막은 `<EmailRequiredGate deferCheck>`, 약관 막은 `<ReconsentGate deferCheck>` 로 로그인 직후 확인을 미룬다(sample `EmailGate` · `LegalGate`: `useSyncExternalStore(outer.subscribe, () => outer.getState().status === 'required' || !outer.isReady())`). 안 그러면 두 막이 함께 열려 안쪽 화면이 바깥 막의 `inert` 아래에서 떠 첫 포커스를 잃는다. 풀리면 그때 한 번 묻고, **계정이 없는(로그아웃한) 동안은 풀려도 묻지 않는다** — 취소할 수 없는 대기를 두지 않으므로 아이디 막의 「로그아웃」 뒤에 토큰 없는 `me` 가 나가 「계속하려면 로그인해 주세요」가 뜨지 않는다.
8. `createAuthRoutes({ loginIdRequired, emailRequired })` — 설정에서 아이디를 정하면(`onLoginIdChosen`) / 이메일을 등록하면 막이 접히고 붙잡힌 호출이 풀린다. `paths.forgotLoginId` 는 필수 키다(기본 `/forgot-id`).

남는 위험: 계정이 바뀐 **직후** 늦게 도착한 이전 계정의 403 은 새 계정의 막을 열 수 있다(`setAccount` 가 바뀐 때의 화면 · 붙잡은 호출만 접는다 — 이미 있던 이메일 막과 같은 동작). 열린 막은 서버에 다시 묻는 순간 접힌다.

**설정의 모양** — `AccountSettings` 는 카드 세 장(계정 · 로그인 · 보안 · 환경)에 항목을 한 줄씩(이름 · 현재 값 · 테두리 단추)만 그리고, 입력 · 목록 · 긴 설명은 단추가 여는 대화상자에 둔다. 구역 부품(`EmailSection` …)을 따로 쓰면 `row` 없이 제목 있는 카드 한 장에 그 줄 하나가 담기고, `row` 를 주면 줄만 나와 `SettingsGroup`(`@skeleton/ui`) 안에 직접 놓을 수 있다. 「환경」 카드에 앱의 줄을 더하려면 `settings.preferenceRows`(예: `<ConsentSettings row />`).

**두 이메일 — 계정 이메일 · 연락받을 이메일** — 설정의 「계정 이메일」은 로그인 · 비밀번호 찾기 · 보안 알림에 쓰이고 바꿀 수만 있다(이메일 필수 앱에서는 지울 수 없다고 문구로 말한다). 「연락받을 이메일」(`settings.contactEmail: true` 또는 `AccountSettings contactEmail` · 서버 `contact-email.enabled`)은 **선택** 한 개 — 공지 · 서비스 알림만 가고 로그인 · 복구 수단이 아니다. 등록 = 주소 → 그 주소로 간 인증번호(`ContactEmailSection` — 같은 `VerifyCodePanel`) → 끝, 바꾸기도 같고 지우기는 바로(없으면 「계정 이메일로 받아요」). 서버가 기능을 끄면(`404`) 구역이 스스로 사라진다. 보안 메일(인증번호 · 재설정 · 링크 로그인)은 늘 계정 이메일로만 간다 — 비밀번호 찾기에 연락받을 이메일을 넣어도 메일이 가지 않는다(e2e 가 메일함으로 단정한다).

**다시 인증 — 계정에 맞는 하나** — 이메일 변경 · 첫 비밀번호 · 소셜 연결 · 연결 해제 · 계정 삭제는 서버가 다시 인증을 강제한다. 화면은 `me` 로 종류를 고른다(`reauthKindOf`): **비밀번호**가 있으면 현재 비밀번호 · 없고 주소가 있으면 **메일로 받은 6자리**(`POST /account/reauth/confirmation` — 계정 + 이 세션에 묶임 · 30분 · 5번, 삭제는 별도의 `delete/confirmation`) 를 같은 자리에서 입력(`ReauthProof` 안의 `CodeEntry` — 서버 검증은 작업 요청이 한다: 틀리면 남은 횟수, 만료면 새로 받기) · 주소도 없으면(Naver 등) 이미 연결된 **제공자로 동의를 다시** 거친다(`socialReauth {provider, authorizationCode, redirectUri?}`). 제공자 왕복은 `createSocialLinkFlow().start(provider, { accountId, action })` — 하려던 작업과 계정이 OAuth `state` 기록에 묶여 있어(한 번 읽으면 지워진다 · 같은 콜백을 두 번 읽어도 같은 결과 → StrictMode 안전) 다른 계정이 시작한 왕복은 이어 가지 않는다. 돌아오면 `/account/link-callback` 이 새 인가 코드를 들고 설정 화면으로 돌아가 하려던 작업(이메일 변경 · 해제 · 삭제)을 **한 번만** 이어서 한다. 소셜 연결은 제공자에 다녀온 **뒤** 증거를 받고(서버가 제공자 코드를 바꾸기 전에 증거를 보므로 틀려도 같은 코드로 다시), 주소 없는 계정의 연결은 연결할 제공자의 코드를 `state` 에 묶어 다른 제공자의 동의를 거친 뒤 두 코드로 한 번에 낸다. 주소가 없는 계정은 첫 비밀번호를 정할 수 없다(서버가 인증된 주소를 요구) — 안내만.

**이메일 변경 = 새 주소의 인증번호** — `POST /account/email/change`(다시 인증 포함) → 새 주소로 6자리 → 같은 세션에서 `POST /account/email/change/confirm {code}`(204 — 이 세션만 남고 다른 세션은 끊긴다, `me` · 세션 목록을 다시 읽는다). 단계는 `GET /account/me` 의 `pendingEmail` · `pendingEmailExpiresAt` 가 정한다 — 서버가 요청이 끝나기 전에 저장하므로 새로고침해도 코드 단계가 그대로 열린다(남의 주소면 서버가 같은 것을 보여 준다 — 존재를 숨긴다). 서버에 **취소 엔드포인트는 없다**: 「코드 다시 받기」는 같은 폼(다시 인증 포함)을 다시 제출하는 새 요청이 이전 것을 대신하는 것이고, 안 쓰면 만료된다.

**토큰 갱신** — `createSessionRefresher` 를 클라이언트의 `recoverUnauthorized` 에 꽂는다: 401 → 갱신 한 번(동시에 여러 요청이 401 이어도 한 번, 다른 요청 · 탭이 이미 갱신했으면 호출 없이) → 같은 요청 한 번 재시도. 새 리프레시 토큰을 먼저 저장하고(옛 것은 두 번 보내지 않는다 — 재사용은 서버가 세션을 끊는다), 탭 사이는 `navigator.locks` + `storage` 이벤트(`crossTab`)로 맞춘다. `AUTH.REFRESH_INVALID` · `REFRESH_REUSED` · `ACCOUNT_SUSPENDED` 면 두 저장소를 비우고 `onSessionEnded(reason)`. **`429 AUTH.TOO_MANY_REFRESHES`**(세션이 10분에 30번 넘게 회전)는 세션이 멀쩡하다는 뜻 — 로그아웃하지 않고 그 429 를 일시 오류로 내보낸 뒤, `Retry-After`(없으면 30초, 연속이면 두 배씩, 최대 10분)가 지나기 전에는 서버를 다시 부르지 않고 같은 오류를 돌려준다. 전달 방식 `body`(기본) | `cookie`(`createAuthApi(client, { delivery })` · `createApiClient({ withCredentials })` · 백엔드 `skeleton.auth-session.delivery`). 서버 렌더에서는 import 때 아무것도 읽지 않는다.

**로그아웃 · 계정 전환 때 서버 상태 비우기** — `onAccountChange(session, () => queryClient.clear())` 한 줄(앱의 `src/app/queryClient.ts`). 로그인한 계정이 사라지거나 바뀔 때마다(로그아웃 버튼 · 다른 탭의 로그아웃 · 갱신 실패 · 복구할 수 없는 401 · 링크 · 소셜로 다른 계정이 들어올 때) 불린다. 처음 로그인과 같은 계정의 토큰 갱신은 아니다. 쿼리 키에 계정이 없는 앱이 이전 사람의 데이터를 다음 사람에게 보이지 않게 한다.

**저장 키 이름공간** — 같은 출처에 앱 둘을 경로로 나눠 올려도 토큰 · 락이 섞이지 않게 `authStorageKeys('my-app')` 로 키를 만든다(`<ns>.accessToken` · `.refresh` · `.auth.refresh`(락) · `.returnTo` · `.social.` · `.social-link.`(제공자 왕복의 하려던 작업 · 계정) · `.signUp`). `createAuthRoutes({ namespace })` 에도 같은 이름을 준다. 생략하면 옛 이름 `skeleton`. 앱의 `AUTH_NAMESPACE` 는 `new-project.sh` 가 새 프로젝트 이름으로 찍는다.

**일회용 링크 도착 화면** — 비밀번호 재설정과 링크 로그인뿐이다. 링크 로그인은 도착하면 바로(계약이 마운트 POST 를 허용). 읽은 토큰 · OAuth 코드는 `history.replaceState` 로 주소창에서 지운다(`scrubUrlParams`). 앱 껍데기에는 `<meta name="referrer" content="no-referrer">` 를 둔다(서버는 `Referer` 에 기대지 않는다 — CSRF 는 `X-Requested-With` 헤더 · SameSite · CORS).

**쿠키 모드 — 한 줄 스위치** — 앱의 `src/auth/authConfig.ts` 의 `DEFAULT_REFRESH_DELIVERY = 'body'` 를 `'cookie'` 로(또는 `.env` 에 `VITE_AUTH_REFRESH_DELIVERY=cookie`). 짝지을 백엔드 설정은 `skeleton.auth-session.delivery=cookie`(리프레시 토큰이 HttpOnly · Secure · `SameSite=Strict` 쿠키 `skeleton_refresh` 로만 오가 스크립트가 못 읽는다 — XSS 에 강하다). 조건: 프런트와 API 가 **같은 사이트**(개발은 Vite 프록시 · 배포는 같은 도메인의 리버스 프록시), 갱신 · 로그아웃은 `X-Requested-With: fetch` 와 자격 증명 포함으로 나간다(앱이 `withCredentials` 로 이미 건다). 기본은 `body` + `localStorage`(탭 여러 개 · 새로고침에서 로그인 유지, 대신 XSS 에 리프레시 토큰이 노출) — 어느 쪽이 맞는지는 위협 모델이 정한다. `cookieDelivery.test.ts` 가 이 길(CSRF 헤더 · 자격 증명 · 저장소에 토큰 없음 · 짝이 안 맞을 때 한 번만 실패)을 통합해서 지킨다.

**갱신 도중 페이지가 이동하면**(응답을 잃는다) — 백엔드 `reuse-grace`(샘플 · 스타터 백엔드는 `10s`, 멱등 회전: 직전 토큰을 유예 안에 다시 내밀면 같은 후속 토큰)가 있으면 다음 페이지의 갱신이 이어진다. 모듈 기본 `0s` 에서는 같은 일이 탈취로 보여 세션이 닫힌다 — 클라이언트는 `onSessionEnded('reuse-detected')` 로 한 번 깨끗이 로그아웃하고 멈춘다(루프 없음). 둘 다 `refreshNavigation.test.ts`.

**소셜 `state`** — 로그인 · 연결 모두 `start()` 가 만든 `state` 를 `sessionStorage`(그 탭)에 두고, 콜백은 `state` 가 없거나 이 브라우저가 시작한 것과 다르면 요청 없이 거절한다(`state_mismatch`). 같은 콜백을 두 번 처리해도 요청은 한 번. 반드시 `storage: window.sessionStorage` 를 넘긴다(생략하면 메모리라 제공자에 다녀오면 사라진다).

**선택 내보내기 `@skeleton/auth/admin`** — `AdminAccounts` · `AdminAccountsTable` · `createAdminAccountsApi`(백엔드 `skeleton.account.admin.enabled=true` + `account.read` 권한). 쓰지 않으면 번들에 들어가지 않는다. 가드는 `RequirePermission anyOf={['account.read']}`(권한 없음 = 로그아웃이 아니라 「접근 차단」 안내), `AdminAccounts` 의 `can={useCan()}` 이 정지 · 해제 · 복구(`account.manage`)와 역할 부여(`account.roles`) 메뉴를 가린다.

**권한으로 화면 가리기** — 백엔드가 `GET /auth/me` 의 `permissions`(`payment.refund` … · 전권은 `*`)를 준다. `principal.permissions` 에 들어오고(옛 서버 · 로그인 응답 · 토큰 claim 에 없으면 `[]` 로 채운 뒤 세션이 `/auth/me` 로 다시 읽는다), `hasPermission(list, key | keys)` · `usePermission(key)` · `useCan()`(부품에 `can` prop 으로 넘기는 함수) · `<RequirePermission anyOf={[…]} forbidden={…}>`(로그인 안 함 → 로그인으로, 권한 없음 → 「접근 차단」 안내) 가 읽는다. 화면을 숨길 뿐 진짜 판정은 서버다. `RequireRole` 은 그대로 남는다.

화면은 `Patterns/Auth/*` 스토리(로그인 · 가입 · 아이디 칸 · 아이디 정하기 · 이메일 등록 · 메일 링크 도착 · 계정 설정 · 운영자 표)가 정본이다. 문구는 모두 `labels` prop — 기본 영어, `koAuthLabels` 한국어, 그 밖의 언어는 `AuthLabels` 타입을 채운다(빠진 키는 컴파일 오류).

백엔드 계약(`docs/account-http-contract.md`)에서 이 패키지가 기대는 것: 응답 `AuthTokenResponse.{accessToken, refreshToken?, refreshExpiresAt?, sessionId?}` · 오류 코드 `AUTH.{EMAIL_NOT_VERIFIED, ACCOUNT_SUSPENDED, TOO_MANY_ATTEMPTS, REFRESH_INVALID, REFRESH_REUSED, TOO_MANY_REFRESHES(429 — 세션 유지)}` · `ACCOUNT.{TOKEN_INVALID(410 — 재설정 · 링크 로그인만), CODE_INVALID(400, data.attemptsLeft), CODE_EXPIRED(410), PASSWORD_POLICY(data.violations), CURRENT_PASSWORD_INVALID, REAUTH_FAILED, REAUTH_REQUIRED(403), EMAIL_TAKEN, SIGN_UP_CLOSED, CAPTCHA_FAILED, SOCIAL_EMAIL_CONFLICT, LAST_SIGN_IN_METHOD, RATE_LIMITED(data.retryAfterSeconds)}` · 아이디를 켠 앱의 `ACCOUNT.{LOGIN_ID_TAKEN(409 — 가입 · 인증번호 단계 · 정하기), LOGIN_ID_REQUIRED(403), LOGIN_ID_ALREADY_SET(409)}` · 정책 `GET /account/password/policy` 의 `maxBytes`(문서의 `maxLength` 도 받는다) · `Idempotency-Key`(이메일 변경 · 삭제) · 이메일 변경 확인은 이 세션을 남기고 다른 세션만 닫는다 · 소셜 연결 해제 · 이메일 변경 확인 뒤에는 세션 목록을 다시 읽는다(서버가 다른 세션을 닫는다) · 운영자 호출의 403 은 로그아웃이 아니라 「접근 차단」(저장된 계정이 더는 활성 관리자가 아니어도 토큰은 살아 있다) · 운영자 목록은 `size ≤ 100` · `page ≥ 0` 으로 맞춰 부른다.

## 비밀번호 확인 · 제출이 막혔을 때

- **닉네임 칸**(가입 · 프로필) — 같은 낱말 「닉네임」/"Nickname"(`labels.displayName`). 가입 화면은 `displayName`(`'off'` 기본 · `'optional'` · `'required'`)로 정한다(`createAuthRoutes({ signUp: { displayName: 'required' } })`). 옛 `askDisplayName`(true = `optional`)도 그대로 — `displayName` 이 있으면 그쪽이 이긴다. 앞뒤 공백을 떼고 1..60 코드 포인트, 필수인데 비우면 `FormProblems` 로 안내(`problemDisplayNameMissing`). 서버가 닉네임을 필수로 켠 환경에서 빠진 가입은 `400`(필드 `displayName`)이 칸 아래에 보인다. 닉네임 중복 금지 서버의 `409 ACCOUNT.DISPLAY_NAME_TAKEN` → 「이미 쓰고 있는 닉네임이에요」: 가입 제출이면 칸 아래, **인증번호 단계에서 오면 시도가 닫히지 않으니 그 자리에서 닉네임만 다시 입력**받아 같은 코드로 다시 확인(비밀번호 재입력 없음, 남은 시간 계속), 프로필 수정이면 칸 아래. 닉네임 변경 한도(`429`)는 「너무 자주 바꿨어요. {시간} 뒤에」, 규칙 위반(`Required` · `Size` · `Pattern` · `Reserved`)은 우리 문구로 — `#` · `@` 는 보내기 전에 막고 길이는 코드 포인트로 센다. 서버가 `resendAvailableAt: null` 을 주면(더 다시 보낼 수 없다) 「다시 받기」를 숨기고 안내한다. 꼬리표 방식 서버(`GET /account/me` 의 `displayTag`)면 프로필 절이 `닉네임#번호` 한 줄과 복사 버튼을 보인다(`displayNameShownAs`). **`showDisplayName: false`**(`AccountSettings` · `createAuthRoutes({ settings })`, 기본 `true`): 글 · 댓글의 이름을 작성 닉네임(`@skeleton/author-profile`)으로 따로 쓰는 앱이 계정 닉네임 줄(칸 · `닉네임#번호` · 복사)을 화면에서 숨긴다 — 사용자에게 닉네임이 둘이 되지 않게. 언어 · 시간대만 남고 닉네임은 저장 요청에도 실리지 않는다(가입 화면의 닉네임 칸은 `signUp.displayName` 그대로).
- **비밀번호 확인 칸**(`confirmPassword`, 기본 **켜짐**) — 가입 · 비밀번호 재설정 · 비밀번호 변경 · 첫 비밀번호 정하기. 확인 칸을 건드린 뒤부터 일치 여부를 바로 알려 주고(「비밀번호가 일치하지 않아요」 / 「일치해요」), 다르면 제출하지 않는다. 「보기」 하나가 두 칸을 함께 보이고, 둘 다 `autocomplete="new-password"` 이며 붙여넣기를 막지 않는다. 성공하면 두 칸이 함께 비워지고 **확인 값은 API 로 가지 않는다**. 끄기: `<SignUpScreen confirmPassword={false} />` · `<ResetPasswordScreen confirmPassword={false} />` · `<PasswordSection confirmPassword={false} />` · `<AccountSettings confirmPassword={false} />`, 또는 `createAuthRoutes({ confirmPassword: false })`(가입만 따로: `signUp: { confirmPassword }`). 문구: `passwordConfirm` · `passwordMismatch` · `passwordConfirmMissing` · `passwordMatches`(ko · en 사전에 있다).
- **제출이 막히면 반드시 말한다** — 가입 · 로그인 · 비밀번호 찾기 · 재설정 · 비밀번호 변경 · 이메일 변경 · 소셜 연결 본인 확인 · 계정 삭제에서, 비었거나 틀린 채로 제출 버튼을 누르면 ① 버튼 바로 위에 `role="alert"` 요약(`@skeleton/ui` 의 `FormProblems` — 줄은 그 칸으로 데려가는 버튼) ② 첫 틀린 칸으로 포커스 + 스크롤 ③ 틀린 칸에 오류 테두리 + `aria-invalid`. 고치면 곧바로 사라진다. **제출 버튼은 꺼 두지 않는다**(본인 확인 전의 「계정 삭제」 · 「비밀번호 변경」도 눌리고 이유를 말한다). 문구: `formProblemsTitle` · `problemEmailMissing` · `problemEmailInvalid` · `problemPasswordMissing` · `problemPasswordRules` · `problemConsentMissing` · `problemProofMissing`.
