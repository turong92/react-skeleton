# @skeleton/payment

결제 **한 벌** — 장부 API · TanStack Query 훅 · 토스 결제창 열기 · 돌아온 주소 읽기 · 오류 코드, 그리고 장부 없이 쓰는 **얇은 호출**. 운영자 화면 부품은 선택 하위 경로 `@skeleton/payment/admin`(아래 「운영자 부품」). 의존: `@skeleton/api-client` (훅은 `@tanstack/react-query` · `react` 를 peer 로).

두 갈래가 있고 서로 섞이지 않는다.

| 갈래                                                                             | 언제                                                                                                                | 백엔드                                                                                                                                             |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **장부** — `createPaymentLedgerApi` · 훅 · `openCheckout` · `readCheckoutReturn` | 주문을 서버가 만들고 금액을 서버가 정하는 결제(응원하기 · 상품 구매). 기본 경로가 있다(`/payments`)                 | `payment` + 장부 저장 모듈 `payment-jdbc` + 결제사(`payment-toss`) — HTTP 계약은 백엔드 `docs/payment-http-contract.md`(결제 장부와 함께 들어온다) |
| **얇은 호출** — `createPaymentApi` · `confirmRequestFromTossRedirect`            | 장부 없이 앱이 자기 컨트롤러로 `PaymentService` 를 부르는 앱. **기본 경로 없음**(없는 엔드포인트를 가정하지 않는다) | `payment` + `payment-toss` \| `payment-stripe`. HTTP 는 앱                                                                                         |

## 장부 — 쓰는 법

```ts
const ledger = createPaymentLedgerApi(apiClient) // { basePath = '/payments' }

// 1) 누르면: 주문을 만들고(서버가 금액을 정한다) 결제창을 연다.
//    훅이 한 의도의 Idempotency-Key 를 들고 있어 같은 상품을 다시 보내면 서버가 같은 주문을 돌려준다 — 그래도 `press()` 가 끝날 때까지 단추를 막는다
//    (`create.isPending` 만 보면 주문이 만들어진 뒤 결제창이 뜨기 전 틈에 단추가 다시 열린다)
const create = useCreateOrder(ledger)
const abandon = useAbandonOrder(ledger)
const [busy, setBusy] = useState(false)
// <Button loading={busy} onClick={press}>응원하기</Button>
async function press() {
  if (busy) return
  setBusy(true)
  try {
    const { checkout } = await create.mutateAsync({ itemType: 'cheer', itemRef: 'cheer-3000' })
    await openCheckout(checkout, {
      successUrl: `${location.origin}/payments/return`,
      failUrl: `${location.origin}/payments/return`,
    })
  } catch (e) {
    // 사용자가 결제창을 닫았다 — 주소가 바뀌지 않으니 우리가 그만둠을 알린다
    if ((e as { code?: string }).code === 'USER_CANCEL') await abandon.mutateAsync(checkout.orderId)
    else throw e
  } finally {
    setBusy(false)
  }
}

// 2) 돌아온 곳(/payments/return): 주소를 읽고, 승인하고, 서버가 읽어 주는 주문으로 결과를 그린다
const back = readCheckoutReturn(location.search) // 못 읽으면 PaymentRedirectError — 오류 화면으로
const confirm = useConfirmOrder(ledger) // 결과를 모르면(네트워크 · 시간 초과 · 5xx · 401) 같은 주문의 승인을 알아서 다시 보낸다
useEffect(() => {
  if (back.ok)
    confirm.mutate({
      orderId: back.orderId,
      providerPaymentId: back.providerPaymentId,
      amount: back.amount,
    })
  else if (back.orderId) abandon.mutate(back.orderId) // back.code 는 결제사 코드 — 화면 문구는 우리가 고른다
}, []) // 두 번 돌아도(StrictMode · 새로고침) 서버가 같은 답을 준다
const detail = useOrder(ledger, back.orderId ?? undefined) // CONFIRMING 이면 알아서 되묻는다
// 단계는 부품이 정한다: 서버가 읽어 준 주문이 끝 상태면 그것이, 아니면 승인 호출의 마지막 오류가
// <PaymentResult order={detail.data?.order} error={confirm.error} onViewHistory={…} onRetry={…} labels={koPaymentLabels} />
// 다시 보내는 동안 confirm.error 는 비어 있다(isPending) — 「결제 확인 중」. 다 쓰고도 모르면 「확인이 늦어지고 있어요」.

// 3) 결과: 승인이 202(CONFIRMING)였으면 끝날 때까지 알아서 되묻는다
const { data } = useOrder(ledger, orderId) // data.order.status, data.refunds
```

- **금액은 주소에서 왔다 — 사용자가 고칠 수 있다.** 승인 요청의 `amount` 는 서버가 주문의 금액과 대조한다(`400 PAYMENT.AMOUNT_MISMATCH`). 브라우저가 금액을 정하는 길은 없다 — `createOrder` 는 상품 코드(`itemType` · `itemRef`)만 보낸다.
- **같은 의도는 같은 키로 — 훅이 들고 있다.** `useCreateOrder` · `useRequestRefund` 는 `Idempotency-Key` 를 항상 보내고, 입력이 같으면(`itemType` · `itemRef` · `quantity` / `orderId` · `reasonCode` · `amount`) 같은 키를 다시 쓴다 — 연속 두 번 누름 · 네트워크 오류 뒤 다시 누름 · 앱이 켠 `mutations.retry` 가 같은 요청이 된다. 입력이 바뀌거나 **성공하면**(그 호출이 쓴 키가 지금 든 키일 때만 — 그 사이 다른 입력으로 넘어갔다면 그 키는 남는다) 새 키고, 든 지 10분(`INTENT_KEY_TTL_MS`)이 지난 키도 새로 만든다. 변수 `idempotencyKey` 를 주면 그것이 이긴다. API 함수(`createOrder` · `requestRefund`)를 훅 없이 부르면 호출마다 새 키(`newIdempotencyKey()`)다. 그래도 누르는 동안은 단추를 막는다(위 `press()`).
- **`useOrder(api, id, { maxPollMs? })`**: `CONFIRMING`(승인 결과를 아직 모름)인 동안만 1초에서 시작해 두 배씩(최대 10초) 늘려 가며 다시 묻는다. 끝 상태(`PAID` · `FAILED` · `EXPIRED` · `CANCELED` · `PARTIALLY_REFUNDED` · `REFUNDED`)이거나 첫 `CONFIRMING` 답으로부터 `maxPollMs`(기본 5분, `ORDER_POLL_MAX_DURATION_MS`)가 시계로 지나면 멈춘다(조회가 계속 실패해도 시계는 간다) — 그때 화면은 이미 「결제 내역에서 다시 볼 수 있어요」(`PaymentResult` 의 「늦어지고 있어요」, 기본 30초 뒤)다. 간격은 `CONFIRMING` 을 받은 횟수로 늘어난다(이전 조회 · 무효화는 세지 않고, 조회 하나가 실패해도 간격은 그대로다). **`PENDING` 은 되묻지 않는다** — 서버가 아직 승인 요청을 받지 않은 것이라 되물어도 달라지지 않는다. 그 길은 아래 승인 다시 보내기가 맡는다.
- **승인 호출은 45초까지 기다린다.** 승인은 결제사 응답을 기다리는 동기 호출이고 백엔드가 그 제한을 30초로 둔다 — 클라이언트 기본 15초에 끊기면 느리지만 성공한 승인이 네트워크 오류가 된다. `createPaymentLedgerApi(client, { confirmTimeoutMs })`(기본 `CONFIRM_TIMEOUT_MS` = 45초)로 바꾼다. 앱 클라이언트의 `timeoutMs` 가 더 짧아도 이 호출은 요청별 값이 이긴다.
- **승인 오류는 세 갈래다 (`confirmOutcomeOf(error)`).**
  - `unknown` — 네트워크 오류 · 시간 초과 · 5xx · 401 갱신 실패 · 403 · 408 · 429: 서버가 요청을 받았는지, 받았다면 어떻게 끝냈는지 모른다. `useConfirmOrder` 가 **같은 주문의 승인을 다시 보낸다**(`CONFIRM_RETRY_LIMIT` = 5번, 1초에서 두 배씩 10초까지, 그동안 `isPending`). 서버 계약: `CONFIRMING` 이면 202, `PAID` 면 200, 결제사 멱등 키 = 주문 id — 다시 보내도 두 번 결제되지 않는다. 다 쓰고도 모르면 마지막 오류로 끝나고, 화면은 「확인이 늦어지고 있어요」(「다시 해 보기」 없음)다.
  - `declined` — 402 `DECLINED`: 결제사가 거절했다. 「결제가 안 됐어요」 + 「다시 해 보기」(새 주문).
  - `rejected` — 그 밖의 확정 4xx(400 `AMOUNT_MISMATCH` · 409 `MODE_MISMATCH` · 409 `ORDER_NOT_PAYABLE` · 404): 서버가 이 승인 요청을 받지 않았다. 다시 보내지 않고, 화면은 「결제를 확인하지 못했어요」(스피너 없음 · 「다시 해 보기」 없음 · 「결제 내역」 + 참조 번호).
  - **서버가 읽어 준 주문이 끝 상태(`PAID` · `FAILED` · `EXPIRED` · `CANCELED` …)이면 그 상태가 오류를 이긴다** — 승인 요청이 닿았는데 답만 잃은 경우의 옛 `PENDING` 사본이 아니라 서버의 지금 상태를 본다. `useConfirmOrder` · `useAbandonOrder` 는 성공이든 실패든 끝나면 캐시를 새로 고친다(`onSettled`). 모르는데 「다시 해 보기」를 주면 새 주문이라 두 번 결제될 수 있다.
- **변경 훅은 `paymentKeys.all`(뿌리)를 무효화**한다 — 설정 · 내역 · 한 건이 함께 새로 고쳐진다. 환불 요청 · 거둠 · 승인 · 그만둠은 끝나면(실패 포함 - 확정 거절 409 · 400 은 화면이 낡았다는 말이다), 그리고 **다시 읽기가 끝날 때까지 변경이 `pending`** 이라 단추가 잠긴다(방금 나간 환불이 안 보이는 낡은 화면에서 또 누르지 못하게 — `onSettled` 가 약속을 돌려주는 데 기댄다). 주문 만들기는 하지 않는다(결제하지 않은 시도는 어느 목록에도 없고, 기다리면 결제창이 늦게 열린다).
- **Paddle(해외 결제)**: `checkout.kind === 'PADDLE_CHECKOUT'`(주문) · `billingAuth.kind === 'PADDLE_CHECKOUT'`(구독)이면 `openCheckout` · `openBillingAuth` 가 Paddle.js(`https://cdn.paddle.com/paddle/v2/paddle.js`)를 누른 그때 불러와 **오버레이 결제창**을 연다 — 서버가 Paddle 에 **거래를 먼저 만들고**(가격 · 수량 · 우리 줄 id 는 서버가 정한다) 화면에는 `attributes.transactionId` 만 준다 - `Paddle.Checkout.open({ transactionId })`, 브라우저가 가격이나 customData 를 넘기지 않는다. 약속은 창이 **열리면** 끝난다(완료는 알리지 않는다 — 결제 결과는 웹훅으로 서버에 닿는다). 승인 호출(`confirm`) · 카드 등록 `activate` 가 없으니 돌아온 화면은 서버를 되묻는다: `useOrder(api, id, { untilPaid: true })` · `useMySubscription(api, { subscriptionId })`(반환 주소의 구독 id - 방금 시작한 그 구독이 보이고 `PENDING` 을 벗어날 때까지 되묻는다. `{ untilActive: true }` 만 쓰면 같은 계정의 옛 `ENDED` 구독이 먼저 읽힐 때 그것을 답으로 쳐 재구독 직후 화면이 멈출 수 있다). 결제사는 **서버가 접속 나라로 정한다** — `GET /config` 의 `country` · `provider` · `cancelPolicy`(해지·환불 정책 요약 키)를 그대로 쓰고, `createOrder` · `startSubscription` 은 결제사도 나라도 보내지 않는다(서버가 읽지 않는다). 견본 앱은 한국이면 토스, 그 밖은 Paddle(서버 설정) — `apps/sample/src/payment/CountryPolicyNotice.tsx` 가 나라와 규칙을 보여 주기만 한다. `Subscription.providerManaged` 면 플랜 변경 · 중도 해지는 없고 해지는 기간 끝에만 된다. 시험 · 스토리에서는 `loadPaddle` 로 가짜 SDK 를 넣는다.
- **`openCheckout`**: 토스 SDK v2 스크립트(`https://js.tosspayments.com/v2/standard`)를 **누른 그때** 불러온다(npm 의존 없음 · import 때 `window` 를 읽지 않아 SSR 안전). 구매자 이름 · 이메일 · 전화번호는 넘기지 않는다. 사용자가 창을 닫으면 SDK 가 던진 에러(`code: 'USER_CANCEL'` 등)가 그대로 나온다. 시험 · 스토리에서는 `loadSdk` 로 가짜 SDK 를 넣는다. 모르는 `checkout.kind` 는 던진다. 스크립트 로드는 `window` 별로 한 번(불러오는 중이면 같은 약속), 서버에서 부르면 거절된 약속, `onload`/`onerror` 가 15초 안에 안 오면 포기, 실패하면 붙인 `<script>` 를 떼고 다음 누름이 다시 시도한다.
- **카카오페이 직접 연동(`checkout.kind === 'KAKAOPAY_REDIRECT'`)**: 토스 계약 없이 카카오페이 계약만 있는 사업자용 별도 결제사(백엔드 `payment-kakaopay`). 서버가 결제 준비(`ready`)를 이미 불러서 `attributes.pcUrl` · `mobileUrl`(http(s) 절대 주소만)을 주고 `clientKey` 는 `null` 이다 - `openCheckout` 은 SDK 없이 **구매자를 그 주소로 보낸다**(`isMobile` 이면 모바일 주소, 기본은 `navigator.userAgent`; `successUrl` · `failUrl` 은 쓰지 않는다 - 돌아올 주소는 서버 설정이다). `clientKey` 가 `null` 이어도 열 수 있는지는 `checkoutCanOpen(checkout)` 이 가른다(토스 · Paddle 은 키, 카카오페이는 주소). 구매자가 인증을 마치면 서버 설정의 주소로 `?kind=KAKAOPAY_REDIRECT&provider=<결제사 id>&order=<주문 id>&result=success&pg_token=…`(취소 · 실패는 `result=cancel` · `fail`)이 붙어 돌아오고 `readKakaoPayReturn(search)` 가 읽는다 - **금액도 결제 번호도 주소에 없다**: 화면은 `confirmOrder(id, { amount, approvalToken })` 만 보낸다(`providerPaymentId` 는 생략 - 서버가 주문에 박아 둔 거래 번호를 쓴다). 같은 나라에 결제사가 둘 이상 켜지면 `GET /config` 의 `choices` 가 둘 이상이고, 화면이 고른 id 를 `createOrder({ …, provider })` 로 보낸다(서버는 `choices` 밖의 값을 읽지 않는다).
- **네이버페이 직접 연동(`checkout.kind === 'NAVERPAY_REDIRECT'`)**: 토스 계약 없이 네이버페이 계약만 있는 사업자용 별도 결제사(백엔드 `payment-naverpay`). 서버가 결제를 이미 **예약**했다(`v2/reserve` - 금액 · 주문 번호는 장부의 값이라 구매자가 바꿀 수 없다) - `attributes.windowUrl`(예약 번호가 든 결제창 주소, http(s) 절대 주소만)을 주고 `clientKey` 는 `null` 이다. `openCheckout` 은 SDK 없이 **구매자를 그 주소로 보낸다**(`navigate`; `successUrl` · `failUrl` 은 쓰지 않는다 - 돌아올 주소는 서버 설정이다). 열 수 있는지는 `checkoutCanOpen` 이 가른다. 결제를 마치면 서버 설정의 주소로 `?kind=NAVERPAY_REDIRECT&provider=<결제사 id>&order=<주문 id>&resultCode=Success&paymentId=…`(그만두면 `resultCode=UserCancel`, 그 밖은 `resultCode` · `resultMessage` · `reserveId`)가 붙어 돌아오고 `readNaverPayReturn(search)` 가 읽는다 - **금액은 주소에 없다**: 화면은 읽은 주문의 금액과 그 `paymentId` 를 `confirmOrder(id, { providerPaymentId, amount })` 로 보낸다(토스의 `paymentKey` 와 같은 자리, `approvalToken` 은 없다). 서버는 승인 응답의 총액 · 주문 번호를 주문과 대조해 다르면(다른 주문의 결제 번호 등) `PAID` 로 두지 않는다(화면은 「결제 확인 중」으로 남는다). 인증값이 가맹 심사 뒤에야 나와 진짜 네이버페이로는 돌려 보지 못했다(백엔드 `docs/real-provider-setup.md` §13).
- **간편결제 단추(`EasyPayButtons`)**: 서버 `skeleton.payment-toss.easy-pays`(예 `NAVERPAY, KAKAOPAY, TOSSPAY`)에 코드를 적으면 `GET /config` 의 `easyPays`(결제사 id → 코드 목록)로 나온다 - `easyPaysFor(config, provider)` 가 그 목록을 주고(비면 빈 목록 = 지금 화면 그대로), `<EasyPayButtons codes onPick labels disabled />` 가 카드 단추(앱의 주된 단추) 옆에 테두리 있는 단추를 하나씩 그린다. 눌린 코드는 앱이 주문을 만든 뒤 `openCheckout(checkout, { successUrl, failUrl, easyPay })` 로 넘기면 토스 SDK 에 `card: { flowMode: 'DIRECT', easyPay }` 로 가서 그 앱을 바로 연다. `easyPay` 가 그 주문의 `checkout.attributes.easyPays` 에 없으면 SDK 를 불러오기 전에 던진다. 단건 결제만 - 자동결제(`openBillingAuth`) 카드 등록 창엔 간편결제가 없어 구독 화면에는 내지 않는다. 상점 계약(MID)에 있는 앱만 열린다. 견본: `apps/sample/src/routes/CheerPage.tsx`.
- **거절**: `402 PAYMENT.DECLINED` → `isPaymentLedgerError(e, PaymentLedgerErrorCodes.DECLINED)` · `declineDetail(e)` 가 `{ providerCode?, category? }` 를 준다. 문구는 `category` 로 고르고 결제사 코드는 참조 번호 안에만 둔다.
  - `PAYMENT.DECLINED`(결제 거절)의 `data.category`: `LIMIT_OR_BALANCE | CARD_DECLINED | TEMPORARY | OTHER` — 모르는 값은 `OTHER` 로 본다(`declineCategoryOf`).
  - `PAYMENT.REFUND_DECLINED`(환불 거절)의 `data.category`: `ALREADY_REFUNDED | AMOUNT_EXCEEDED | PARTIAL_NOT_ALLOWED | PERIOD_EXPIRED | TEMPORARY | OTHER` — 앱이 문구를 고를 때 모르는 값은 `OTHER` 로 본다(운영자 환불 창 `AdminRefundDialog` 는 이 분류를 문구로 그린다 - 사용자 쪽 부품은 환불 거절 문구를 그리지 않는다).

## 구독 — 자동결제 (백엔드 `skeleton.payment.subscription.enabled=true` 인 앱만)

플랜 하나를 골라 카드를 한 번 등록하면 기간마다 서버가 알아서 결제한다. 금액의 출처는 앱의 플랜(서버)이고 브라우저는 플랜 코드만 보낸다. 빌링키 · 고객 키는 어떤 응답에도 없다(카드 등록 창 값 `billingAuth.customerKey` 만 예외). 경로 · 오류는 백엔드 `docs/payment-http-contract.md` §12.

```tsx
const api = createSubscriptionApi(apiClient) // { basePath = '/payments' } → /payments/subscriptions/…
const plans = useSubscriptionPlans(api) // [{ code, name, amount, period('P1M'), level }]
const start = useStartSubscription(api) // 같은 플랜을 다시 누르면 훅이 든 같은 Idempotency-Key — 같은 줄, 성공하면 새 키

// 1) 「구독하기」: 구독(PENDING)을 만들고 카드 등록 창을 연다. 성공 주소에 서버가 정한 구독 id 를 실어 둔다(창은 authKey · customerKey 만 덧붙인다)
const { subscription, billingAuth } = await start.mutateAsync({ planCode: 'basic' })
if (billingAuth)
  // 같은 키로 다시 보냈는데 카드를 이미 냈으면 null — 열 창이 없다
  await openBillingAuth(billingAuth, {
    successUrl: `${origin}/subscriptions/return?sub=${subscription.id}`,
    failUrl: `${origin}/subscriptions/return?sub=${subscription.id}`,
  }) // 창을 닫으면 SDK 가 { code: 'USER_CANCEL' } 을 던진다

// 2) 돌아온 곳: 주소를 읽고 첫 결제를 한 번만 보낸다. 결과를 모르면 훅이 같은 구독의 activate 를 알아서 다시 보낸다(서버가 재전송을 안전하게 받는다)
const back = readBillingReturn(location.search) // { ok: true, authKey } | { ok: false, code } — 못 읽으면 PaymentRedirectError
const activate = useActivateSubscription(api)
activate.mutate({ id, authKey: back.authKey }) // 200 ACTIVE · 202 PENDING(첫 결제 확인 중) · 402 PAYMENT.DECLINED(구독은 끝난다)

// 3) 내 구독: PENDING 인 동안만 간격을 늘려 가며 다시 묻는다
const mine = useMySubscription(api) // { subscription | null, orders: 최근 결제 5건 }
useCancelSubscription(api).mutate(id) // ACTIVE → CANCELING(기간 끝까지 이용), PAST_DUE 는 바로 ENDED

// 4) 위 등급으로 바꾸기: 미리보기(지금 결제될 금액) → 그 금액을 expectedCharge 로 보낸다
const preview = usePlanChangePreview(api, id, planCode) // planCode 가 null 이면 묻지 않는다
useChangeSubscriptionPlan(api).mutate({ id, planCode, expectedCharge: preview.data.charge.amount })
// data.pendingPlanCode 가 있으면 결제 확인 중(me 가 되묻는다). 거절은 PAYMENT.DECLINED(플랜 그대로), 금액이 올랐으면 409 PLAN_CHANGE_CHARGE_CHANGED
```

- 변경(`activate` · `cancel`)이 성공하든 실패하든 `paymentKeys.all` 뿌리를 무효화하고, 그 약속이 끝날 때까지 `pending` 이다(낡은 화면에서 한 번 더 누르지 못한다). `start` 는 무효화하지 않는다 - 시작만 한 `PENDING` 은 `me` 에 보이지 않고 기다리면 카드 창이 늦게 열린다.
- 새 오류 코드: `SUBSCRIPTION_NOT_FOUND`(404) · `ALREADY_SUBSCRIBED` · `SUBSCRIPTION_NOT_ACTIVATABLE` · `SUBSCRIPTION_NOT_CANCELABLE` · `PLAN_CHANGE_NOT_ALLOWED` · `PLAN_CHANGE_CHARGE_CHANGED`(409) — `PaymentLedgerErrorCodes` / `isPaymentLedgerError` 에 들어 있다.
- 화면 부품(문구는 `labels.subscription`, ko · en 둘 다): `SubscriptionPlanList`(`plans` · `onSubscribe(plan)` · `busyPlanCode?` — 카드마다 이름 · 「3,900원 · 1개월마다 결제」 · 채운 「구독하기」 하나) · `SubscriptionStatusBadge`(`status`) · `MySubscriptionCard`(`subscription` · `orders` · `onCancel?` · `renderOrderAction?` — 플랜 · 상태 · 다음 결제일(해지 예약이면 「○○에 끝나요」) · 카드 끝 네 자리 · 최근 결제 · `onCancel` 의 「기간 끝에 해지」 · `onCancelNow` 의 「지금 해지하고 환불」(둘은 같은 무게의 테두리 단추, 정책이 중도 해지를 닫았으면 부모가 `onCancelNow` 를 주지 않는다, 해지 예약 중에도 보인다), 끝난 구독은 `endReason` 별 안내) · `CancelSubscriptionDialog`(`open` · `onClose` · `onConfirm` · `subscription` · `busy?` · `error?`) · `CancelNowDialog`(`open` · `onClose` · `onConfirm` · `preview?`(`useCancelPreview`) · `previewLoading?` · `busy?` · `error?` — 환불 예정 금액과 계산 내역(낸 금액 - 이용한 만큼 - 위약금)을 보이고 읽기 전에는 확인이 잠긴다; 금액이 시간에 따라 변하니 창을 열 때 `refetch()`) · `CancelNowResultNotice`(`result` — 해지한 직후 얼마를 돌려주는지 · 처리 중 · 환불 실패를 말하는 띠) · `ChangePlanDialog`(`open` · `onClose` · `onConfirm({ planCode, expectedCharge })` · `plans`(윗등급만) · `planCode` · `onPlanChange` · `preview?` · `previewLoading?` · `busy?` · `error?` — 지금 결제될 금액을 미리 보이고, 읽기 전에는 확인이 잠긴다; `MySubscriptionCard` 의 `onChangePlan` 이 채운 「플랜 올리기」를 켠다). 플랜 이름을 번역하려면 `name` 을 바꿔 넘긴다(견본 앱은 코드로 된 번역을 우선하고 없으면 서버 이름).
- `priceEveryDisplay(amount, period, labels, locale?)` 가 「3,900원 · 1개월마다 결제」을 만든다 — 읽을 수 없는 주기는 코드를 그리지 않고 금액만.

## 장부 API (`createPaymentLedgerApi(client, { basePath })`)

| 메서드                                                                 | HTTP                                                    | 응답 · 오류                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `config()`                                                             | `GET /config`                                           | `{ available, testMode, refundRequestsEnabled }`                                                                                                                                                                                                                                                                                                                    |
| `createOrder(input, { idempotencyKey? })`                              | `POST /orders` + `Idempotency-Key`                      | `{ order, checkout }` · `409 IDEMPOTENCY_CONFLICT` · `422 ITEM_NOT_PURCHASABLE` · `503 UNAVAILABLE`                                                                                                                                                                                                                                                                 |
| `confirmOrder(id, { providerPaymentId, amount })`                      | `POST /orders/{id}/confirm`                             | `PAID`(200) 또는 `CONFIRMING`(202) 주문 - **`CONFIRMING` 인 주문에 다른 결제 키로 승인을 보내도 409 가 아니라 `202` + 지금 주문이고 새 키는 버려진다**(결과 화면은 서버가 읽어 준 `CONFIRMING` 으로 그대로 「확인 중」이다). 오류: `400 AMOUNT_MISMATCH` · `402 DECLINED` · `409 ORDER_NOT_PAYABLE`(이미 결제된 주문에 다른 키를 보냈을 때도) · `409 MODE_MISMATCH` |
| `abandonOrder(id)`                                                     | `POST /orders/{id}/abandon`                             | 주문(이미 끝났으면 지금 상태 그대로 — 오류가 아니다)                                                                                                                                                                                                                                                                                                                |
| `getOrder(id)`                                                         | `GET /orders/{id}`                                      | `{ order, refunds }`                                                                                                                                                                                                                                                                                                                                                |
| `listOrders({ cursor?, size? })`                                       | `GET /orders`                                           | 커서 응답(최신순, 결제하지 않은 시도는 빠진다)                                                                                                                                                                                                                                                                                                                      |
| `requestRefund(orderId, { reasonCode, amount? }, { idempotencyKey? })` | `POST /orders/{id}/refund-requests` + `Idempotency-Key` | 환불 `REQUESTED` · `409 REFUND_NOT_ALLOWED` · `409 REFUND_IN_PROGRESS` · `400 REFUND_AMOUNT_EXCEEDED`. 돈은 움직이지 않는다 — 운영자가 승인한다                                                                                                                                                                                                                     |
| `withdrawRefund(refundId)`                                             | `POST /refunds/{id}/withdraw`                           | 환불(`REQUESTED` 일 때만) · `409 REFUND_NOT_ALLOWED`                                                                                                                                                                                                                                                                                                                |

남의 것 · 없는 것은 모두 `404 ORDER_NOT_FOUND` / `REFUND_NOT_FOUND`. 코드는 `PAYMENT.` 접두사가 붙는다(`PaymentLedgerErrorCodes`).

## 얇은 호출 — 장부 없이

```ts
const payment = createPaymentApi(apiClient, {
  paths: { confirm: '/orders/pay/confirm', route: '/skeleton/payments/route' }, // 준 것만 생긴다
})

const request = confirmRequestFromTossRedirect(location.search, { currency: 'KRW' })
const done = await payment.confirm!(request, { idempotencyKey: newIdempotencyKey() }) // → PaymentOperationResult
if (done.status !== 'CONFIRMED') …                                                    // PENDING · FAILED · UNKNOWN 도 온다
```

**금액 검증은 서버 몫이다.** 리다이렉트의 `amount` 는 사용자가 고칠 수 있다 — 앱 컨트롤러가 주문의 실제 금액과 대조한 뒤 `PaymentService.confirm` 을 부른다. 이 갈래의 `createPaymentApi` 는 그것을 대신하지 않는다.

```tsx
import { koPaymentLabels, OrderList, OrderSummary, PaymentResult, RefundRequestDialog } from '@skeleton/payment'

<PaymentResult order={order} error={confirmError} onViewHistory={…} onRetry={…} labels={koPaymentLabels} />

// 열 때 request.reset() — 지난번 오류가 다시 열린 창에 남지 않게. onConfirm 은 창이 보인 금액을 amount 로 준다

```

## 운영자 부품 — `@skeleton/payment/admin`

`@skeleton/auth/admin` 처럼 **선택 하위 경로**다. 백엔드는 `skeleton.payment.admin.enabled=true`(기본 꺼짐)와 ADMIN 역할이 필요하고, 검사는 서버가 한다(화면은 `RequireRole` 로 보여 줄지만 정한다). 문구는 같은 `labels` prop 의 `admin` 가지(`koPaymentLabels.admin`)다 — 한 벌로 넘기면 된다. 낱말은 사용자 쪽과 같다: 돈을 돌려주는 일은 늘 「환불」(「승인」 · 「반려」 · 「취소」 없음), 맞추는 일은 「결제사와 맞추기」, 사고는 「확인 필요」(`labels.test.ts` 가 운영자 키까지 고정한다).

**계약 대조에서 확인한 것 (백엔드 `docs/payment-http-contract.md` §6 · §11)**

- 운영자 응답의 환불 줄 `failureCode` 에 우리 코드가 온다: `NOT_APPLIED` · `PROVIDER_PENDING` · `RESULT_MISMATCH` · `ORDER_REFUNDED` · `LATE_RESULT`(닫힌 줄에 환불됨 응답이 늦게 왔다 - 돈이 나갔을 수 있어 「다른 환불 줄과 환불된 금액을 확인해 주세요」라고 말한다) · `REFUND_DECLINED`(결제사가 코드 없이 확정 거절). 화면은 아는 코드를 문장으로, 모르는 코드(결제사 거절 코드)는 코드 그대로 그린다. `SUCCEEDED` 줄에 `RESULT_MISMATCH` 가 남을 수 있고 그때도 문장 하나로 조용히 말한다.
- 이력(`events[].providerCode`)에만 남는 코드 둘은 문장으로 읽는다(`labels.admin.eventCodes`): `PROVIDER_PENDING_EXPIRED`(줄에는 안 찍힌다 - 이력 이름 옆에 문장) · `LATE_RESULT`(이력 종류가 `REFUND_UNKNOWN` 이라 이름이 「환불 결과를 아직 몰라요」로 읽히니, 문장이 그 이름을 대신한다). 그 밖의 `providerCode`(`REFUND_LANDED` · `REFUND_MISMATCH_CLEARED` · 결제사 코드 · 확인 필요 사유 이름)는 참조 번호에 그대로 둔다.
- 운영자 응답의 환불 줄에도 `closedBy` 가 온다(`WITHDRAWN` 줄만 값이 있고 다른 상태는 `null`) - 화면은 그것을 따른다(알약 「환불이 끝나 요청이 닫혔어요」). `closedBy` 만 읽는다(`null` 이면 본인) - 이유 코드(`ORDER_REFUNDED`)로 짐작하지 않는다.
- 환불 줄의 `origin` 에 `PROVIDER`, `reasonCode` 에 `PROVIDER_CONSOLE` 이 올 수 있다(결제사 관리 화면에서 취소한 것을 장부가 맞춰 넣은 줄 - 사용자 한 건 응답에도 나온다). 화면은 행위자 「결제사」 · 사유 「결제사에서 환불됨」으로 말한다.
- 주문 만들기 응답의 `checkout` 은 같은 `Idempotency-Key` 를 다시 보냈는데 주문이 이미 `PENDING` 이 아니면 `null` 이고(`200`), `clientKey` 도 `null` 일 수 있다 - 견본 앱은 `checkout: null` 을 **주문 상태로** 가른다: `PAID` · `CONFIRMING` · 환불 계열이면 실패가 아니라 그 결제의 화면(`/payments/:id`)으로 보내고, 그 밖(닫힘)이면 「응원을 시작하지 못했어요」(다음 누름은 새 주문). `clientKey: null`(서버에 결제창 키가 없다)이면 다시 눌러도 안 되니 만든 주문을 돌려놓고(`abandon`) 「지금은 결제를 쓸 수 없어요」로 말한다. 주문 만들기가 `503 PAYMENT.UNAVAILABLE` 이면 클라이언트 키가 없을 때와 같은 막힘이다(「지금은 결제를 쓸 수 없어요」, 화면을 새로 열 때까지 단추를 `aria-disabled` 로 막는다). `429` 면 「다시 눌러 주세요」가 아니라 `retryAfterSeconds` 로 풀리는 **시각**(「… 이후에 다시 눌러 주세요」 - 남은 분은 줄지 않아 말하지 않는다)을 말하고 그 시간 동안 단추를 `aria-disabled` + 이유로 막는다(시간을 못 읽으면 「잠시 뒤에」, 단추는 그대로). `openCheckout` 은 키 없는 결제창 값을 SDK 에 넘기지 않고 던진다.
- 환불 줄의 `closedBy` 는 필수 칸이다(`"USER" | "SYSTEM" | null` - 서버는 사용자 응답에도 늘 보낸다). `WITHDRAWN` 줄만 값이 있고 다른 상태는 `null` 이다. 화면은 `SYSTEM` 이 아니면 본인(`USER`)으로 읽는다. `SYSTEM` 이면 「환불 요청 거둠」이 아니라 「환불이 끝나 요청이 닫혔어요」.

훅: `useAdminOrders` `useAdminOrder` `useAdminRefundRequests` `useAdminWebhookEvents` + 변경 `useOperatorRefund`(의도별 `Idempotency-Key` 를 훅이 든다 — 결과를 모르면 10분이 지나도 든다) `useApproveRefund` `useRejectRefund` `useSyncOrder` `useRetryWebhookEvent`, 그리고 요청 결정 창을 훅에 이은 `useRefundDecision(api, { labels, locale, orderLink?(refund, buttonLikeClassName), onSend? })`(`start(mode, refund, refundable?)` · `dialog` · `approved` — 승인은 `approve` 만, 거절은 `reject` 만 부르고, 일하는 동안 닫았다 다시 열어도 일하는 중이고, 오류로 끝나면 닫힌 창이 다시 열린다)와 직접 환불 창을 이은 `useDirectRefund(api, { order, labels, locale, unsureHoldMs?, unsureFloorMs?, onSend? })`(`ask()` · `dialog` · `done`(방금 나간 환불 줄 — 화면이 「환불했어요」라고 말하는 데) · `forget()`). **낡았을 수 있는 화면**(다시 읽기 실패)에서는 `AdminOrderPanel` 의 `stale` 이 「환불하기」 · 「요청대로 환불하기」를 막고(채운 단추는 「결제사와 맞추기」) `refunded`(환불 줄 — `id` 포함) 가 나간 환불을 상태 글자로 **그 동안에만** 말한다(재조회가 성공하면 환불 줄이 사실을 말한다. 목록에서 줄 id 로 찾아지고 답보다 더 간 상태면 그 줄이 말한다. 두 호출이 있으면 `doneAt` · `approvedAt` 으로 더 최근 것을 고른다). **보내는 중과 결과를 모르는 동안** 직접 환불 창의 금액 · 사유 칸은 잠기고(읽기 전용이되 닿고, 보낸 변수 `sent` 를 보인다) 닫았다 열어도, 닫아 둔 창이 확정 오류로 다시 열려도 보낸 값 그대로다. 「결제사와 맞추기」가 성공하면 `forget()` 이 모름 상태와 든 키를 함께 놓는다(그 뒤의 환불은 새 의도 - 새 키) — **환불을 보낸 지 `unsureHoldMs`(기본 `OPERATOR_REFUND_TIMEOUT_MS` = 45초)가 안 지났으면 놓지 않는다**: 첫 요청이 서버에서 아직 환불 줄을 만들기 전(환불 전 확인 조회 중)일 수 있어 맞추기가 본 장부에 환불 줄이 없을 수 있다(맞추기 결과는 보이되 잠금 · 키는 유지). 유예는 **모름이 된 때가 아니라 보낸 때**(`submittedAt`)부터 센다 - 다시 보내면 다시 센다. 다만 보낸 때가 실제로 나간 때가 아닐 수 있어(오프라인으로 멈췄다 나간 변경 · 앱이 켠 `mutations.retry`) 바닥을 둔다: `max(보낸 때 + unsureHoldMs, 모름이 된 때 + 15초)` - 시간 초과로 모름이 된 보통 경우도 15초 안의 첫 맞추기는 문구와 함께 한 번 기다리게 된다. 유예가 넘어야 하는 것은 서버의 선점 전 구간(환불 전 확인 조회 한 번, 재시도 없음)이다. `forget()` 은 `{ kind: 'release' | 'hold' | 'none', waitMs? }` 를 돌려주고, 못 놓았으면(`hold`) `heldSecondsOf(forget())` 를 `AdminOrderPanel` 의 `syncHeld` 로 주어 「보낸 환불이 아직 가는 중일 수 있어요. 잠시 뒤 다시 맞춰 주세요」를 낭독 가능한 상태 글자로 말하게 한다(초는 쓰지 않는다 - 누른 순간의 값이라 줄지 않는다. 앱은 모름이 풀리면 말하지 않게 `direct.unsure ? held : null` 로 준다). 돈이 결제사와 어긋난 확인 필요(`REFUND_MISMATCH` · `AMOUNT_MISMATCH` · `ORDER_MISMATCH` · `MODE_MISMATCH`)면 `AdminOrderPanel` 이 「환불하기」 · 「요청대로 환불하기」를 「먼저 결제사와 맞춰 주세요」로 막고 채운 단추는 「결제사와 맞추기」다. 이 넷 중 **서버가 환불을 `REFUND_NOT_ALLOWED` 409 로 막는 것은 `REFUND_MISMATCH`** 이고, `MODE_MISMATCH` 는 모드가 실제로 다르면 서버가 `PAYMENT.MODE_MISMATCH` 409 로도 막는다(직접 환불 · 승인 창은 맞추기 쪽과 같은 모드 문장으로 말한다). 나머지는 맞추기를 먼저 권하는 것이다 - 그래서 `onSync` 가 없는 조립에서는 `REFUND_MISMATCH` 만 막고 문구도 「결제사와 어긋나 있어 환불할 수 없어요」다(없는 단추로 보내지 않는다). 맞춘 뒤(`synced`)에도 사유가 남았으면 「맞춰 봤지만 아직 어긋나 있어요. 결제사 화면에서 확인해 주세요」다. 모드가 달라 맞추기가 `409 PAYMENT.MODE_MISMATCH` 로 실패하면 「이 결제는 지금과 다른 쪽(테스트 또는 실제 결제)의 키로 만들어져 지금 키로는 맞출 수 없어요」 - 다시 해 보라고 하지 않는다. 오류 판정: `refundProblemOf(error)`(`declined` · `inProgress` · `notAllowed` · `amountExceeded` · `unavailable` · `notDone` · `otherConfirmed` · `unknown`) · `RefundNotDoneError`. 키는 사용자 쪽과 같은 뿌리(`['payment']`)의 `admin` 가지(`adminKeys`) — 변경이 끝나면 뿌리를 무효화해 같은 브라우저의 사용자 화면도 새로 읽는다.

### 백엔드와 맞춘 곳 (프론트가 가정했던 새 칸 · 코드 — 백엔드 `62d45a5` 에서 맞춰졌다)

프론트가 먼저 가정했던 네 가지는 모두 백엔드 계약 문서(`docs/payment-http-contract.md`, 커밋 `62d45a5`)에 들어왔다. 프론트는 아직 선택으로 받거나 방어를 남겨 두어, 없는 서버에서도 깨지지 않는다.

| 가정                                                                                                                                                | 프론트가 하는 일                                                                                                                                | 없으면                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 운영자 주문 응답의 `accountErasedAt: string \| null`(계약 §1.4)                                                                                     | 「탈퇴한 계정」 표시가 이 칸을 먼저 본다                                                                                                        | `deleted:` 대체 id 로만 가른다(`TOMBSTONE` 모드)                                                        |
| `POST /admin/payments/orders/{id}/sync` 에서 결제사가 그 결제를 모르면 **`404 PAYMENT.PROVIDER_PAYMENT_NOT_FOUND`**(재투입 없이 200 을 주지 않는다) | 「결제사가 이 결제를 찾지 못했어요. 결제사 화면에서 확인해 주세요」. 200 이면 지급 · 회수 사유에 「끝나지 않은 그 일을 다시 걸었어요」를 말한다 | 알 수 없는 오류로 「맞추지 못했어요」, 그리고 200 이면 다시 걸었다고 단정하게 된다                      |
| `GET /payments/config` 의 `available` 이 클라이언트 키가 없으면 `false`                                                                             | 견본 앱이 단추를 막고 「지금은 결제를 쓸 수 없어요」                                                                                            | `clientKey: null` 이 주문 만들기 뒤에야 드러난다 - 화면이 주문을 돌려놓고 같은 말을 한다(방어로 남긴다) |
| 같은 키 재전송에서 `PENDING` 이지만 결제 가능 시간이 지난 주문은 `checkout: null`                                                                   | 실패(「응원을 시작하지 못했어요」)로 말하고 다음 누름은 새 주문                                                                                 | 지난 결제창 값을 그대로 받아 연다                                                                       |

## 테스트가 재지 않는 것

경로 · 메서드 · 본문 · `Idempotency-Key` 헤더(같은 입력이면 같은 키 · 성공하면 새 키), 승인 호출의 제한 시간, 키가 한 뿌리인 것과 변경 뒤 무효화(거둠 · 승인 · 그만둠은 끝나면 실패해도), `CONFIRMING` 에서만 되묻기(간격 · 5분 상한), 결제창 호출 인자(구매자 정보가 없는 것까지), 돌아온 주소 읽기, 오류 코드는 잰다. **재지 않는다**: 실제 백엔드 · 결제사 호출, 진짜 토스 SDK 스크립트(가짜 SDK 로 잰다), 서버 쪽 금액 대조. 화면 부품은 서버 렌더 마크업(`ui.test.tsx`)과 스토리의 `play`(진짜 브라우저 · 접근성 검사)로 잰다 — 낱말 시험은 `labels.test.ts`. 운영자 부품도 같다 — 경로 · 본문 · `Idempotency-Key`(`adminApi.test.ts`), 직접 환불이 결과를 모를 때만 같은 키를 들고 확정 판정에서 놓는 것 · 닫힌 줄을 성공으로 보지 않는 것(`adminQueries.test.ts` · `refundOutcome.test.ts`), 금액 입력 읽기(`amountInput.test.ts`), 마크업(`adminOrderTable` · `adminOrderPanel` · `adminRefundDialog` · `refundRequestTable` · `webhookEventTable` 시험), 한국어 문구에 영어가 남지 않는 것(`adminKorean.test.tsx`), 진입점 분리(`entry.test.ts`). 재지 않는 것: 실제 운영자 API(백엔드 계약 문서와 컨트롤러를 읽어 맞췄을 뿐, 백엔드를 띄워 부르지는 않았다 - 견본 앱 백엔드가 생긴 뒤 e2e 가 한다).
